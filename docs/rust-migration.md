# Перенос FlashForge Device Tab на Rust

Цель — заменить реализацию плагина новой на Rust, сохранив текущие сценарии, настройки и историю. Вкладка продолжит использовать HTML, CSS и JavaScript. Исходная точка для сравнения — текущая рабочая копия, включая незакоммиченные изменения, а не только релиз или коммит `377a251`. Перед началом реализации нужно зафиксировать снимок этой версии отдельно от рабочей копии.

## Ревью текущей реализации

### P1. Команда из монитора может попасть в следующее задание

Монитор отправляет только действие, а карточка задания передаёт ещё имя файла. Сервер читает свежий статус перед отправкой команды только во втором случае. При смене задания в промежутке между отображением и нажатием кнопки монитор всё равно отправляет отмену. Протокол передаёт пустой `jobID` и применяет команду к текущей печати. Карточка задания тоже не отличит два запуска одного файла по одному имени. Прогон на заглушке подтвердил отправку из монитора и отказ для карточки после смены файла. См. `flashforge_device_tab.py:1967`, `:2594`, `:3330`, `:6048`.

Обеим панелям нужен один путь команды со ссылкой на наблюдаемое задание. Если модель отдаёт идентификатор задания, использовать его. Иначе использовать поколение наблюдаемой печати, оценивать смену запуска по телеметрии и заново проверять состояние прямо перед командой. При неоднозначности требовать обновления статуса. На прошивках с пустым `jobID` гарантировать атомарную привязку команды средствами плагина невозможно.

### P1. Опрос может пропустить начало отправки из OrcaSlicer

`begin_upload()` сначала взводит флаг, затем обновляет время. Если читатель попадёт между этими операциями, он может принять новый флаг за просроченный и сбросить его. Прогон с управляемым порядком вызовов подтвердил, что после возврата из `begin_upload()` режим загрузки остаётся сброшенным. Отдельно, текущий код продолжает ожидать конфликтную загрузку не более 1,5 с и возвращается даже при занятом сетевом канале. В хосте за возвратом из события следует вызов `upload()`. См. `flashforge_device_tab.py:4658`, `:4702` и `orca-device-recovery/src/slic3r/Utils/PrintHost.cpp:456`.

Публиковать фазу, поколение и время как одно состояние. При старте закрывать допуск новых операций, прерывать отменяемые операции и проверять уход занятых соединений в пределах бюджета хоста. Текущий API OrcaSlicer передаёт временное имя файла без адреса принтера и не даёт плагину отложить вызов `upload()` после возврата из обработчика. Поэтому использовать общий запрет на конфликтующие операции на время внешней загрузки. Если ограничения хоста не позволяют закрыть конфликтующее соединение вовремя, фиксировать это в диагностике и проверять поведение на реальном хосте.

### P2. Медленный обмен с одним принтером задерживает остальные

Один `printer_lock` обслуживает весь парк. Опрос идёт последовательно, а загрузка файла удерживает блокировку до подтверждения каталога и состояния. Прогон на двух потоках подтвердил, что операция второго принтера ждёт освобождения того же замка. См. `flashforge_device_tab.py:4693`, `:4742`, `:4993`.

Каждому принтеру нужен собственный исполнитель с очередью и ограниченным временем сетевых операций. Один принтер сохраняет порядок команд и эксклюзивность там, где их требует прошивка. Опрос соседнего принтера продолжается, пока первый ждёт ответ или подтверждает загрузку, если общая отправка из OrcaSlicer не активна.

## Архитектура

Один репозиторий, один Rust crate. Отдельные модули внутри него позволяют тестировать обмен с принтером и правила команд без OrcaSlicer. HTML, CSS и JS лежат отдельными файлами и встраиваются в пакет. Существующие страницы и формат ответов локального HTTP сохраняются на первом проходе. Меняются контракты команд, которым нужна проверка задания или подтверждение результата.

| Модуль | Ответственность |
| --- | --- |
| `orca` | Регистрация `orca.plugin`, вкладки и настроек. События хоста, разрешения, уведомления, профили, восстановление штатной страницы и остановка при выгрузке. |
| `printer` | TCP-сессии, HTTP-запросы, поиск в сети, разбор ответов и определение возможностей по модели и телеметрии. Сырые имена файлов из TCP сохраняются как байты. |
| `monitor` | Исполнитель на принтер, расписание опроса, снимки состояния, история заданий в памяти, свежесть данных и общий допуск на время внешней загрузки. |
| `commands` | Проверка состояния, модели, задания и параметров перед отправкой. Различает отказ, отправку без подтверждения, подтверждение и неизвестный исход. Для команд с побочными эффектами неизвестный исход требует сверки состояния перед повтором. |
| `storage` | Чтение старых настроек и JSON, атомарная запись, сохранение повреждённой истории и перенос признака обязательного Home. |
| `web` | Loopback-сервер и раздача ресурсов вкладки. Типизированные запросы, ограничения размера, проверка происхождения запросов, временные файлы и поток камеры. |

Вкладка читает готовые снимки состояния. Команда попадает в очередь нужного принтера, исполнитель проверяет свежие данные и только затем обращается к прошивке. Блокирующий обмен и ожидание подтверждения отделены от потока интерфейса OrcaSlicer. Камера читает поток отдельно, а её команды открытия и закрытия подчиняются правилам работы с принтером. При выгрузке плагина закрывается приём новых запросов, отменяются фоновые операции и сохраняется история.

### Точка входа, разрешения и упаковка

Целевой пакет — Windows x64 `.whl` с модулем PyO3 под Python ABI целевой версии OrcaSlicer. Первым пробуем зарегистрировать пустую вкладку непосредственно из модуля. Если интерфейс регистрации требует Python-классов, оставляем в пакете короткий загрузчик, который объявляет классы хоста и делегирует вызовы Rust. В рабочей логике, состоянии и обработке команд Python тогда не участвует. [Документация PyO3](https://pyo3.rs/main/building-and-distribution)

Импорт `.pyd` предусмотрен в локальном загрузчике, а регистрация требует класс, производный от `orca.base`. Это два отдельных условия. Проба установки должна проверить также повторное включение, отключение, разрешение и отказ для операций с сетью и файлами. Нативный ввод-вывод нельзя считать покрытым Python-аудитом автоматически. Если хост требует посредника для учёта разрешений, сначала проверяем перенос правил через поддерживаемый API или тонкий слой ввода-вывода. Вариант выпуска зависит от результата и правил каталога. См. `PythonInterpreter.cpp:221`, `PythonPluginBridge.cpp:908`, `PluginAuditManager.cpp:4612` в дереве OrcaSlicer.

### Совместимость и возврат

- Проверить переход со старой одноадресной конфигурации и текущего списка принтеров, включая имена, CheckCode, серийные номера и режим вкладки. Проверить идентичность пакета и расположение storage при переходе с `.py` на `.whl`.
- Прочитать `flashforge-*-history.json`, `notifications.json`, `device-pages.json`, `print-sources.json`, `monitor-placement.txt` и `*.manual-home-required`. Сохранить возможность отката на последнюю Python-версию без потери истории или признака обязательного Home. Пробные обновления выполняются на копии пользовательских данных.
- Проверить Adventurer 3/4, 5M/5M Pro, AD5X и Creator 5/5 Pro по матрице поддерживаемых функций. Покрыть разные форматы телеметрии и команды, которые прошивка может принять без наблюдаемого результата.
- Существующие Python-тесты остаются эталоном на время переноса. Старыми ответами прошивок можно питать Rust-тесты, а проверки JavaScript и камеры следует направить на новый сервер. Подтверждать экспериментальные улучшения на тех же входных данных, отдельно от различий реальных прошивок.

## Базовые проверки

В просмотренной рабочей копии прошли 116 Python-тестов, 15 Node-тестов и браузерный сценарий с симулятором камер. Он проверил кадр, снимок, работу нескольких потоков, закрытие вкладки и переподключение. Три отдельных прогона на заглушках подтвердили замечания выше. Проверка Rust-пакета, обновления через Orca Cloud и работа с физическим принтером входят в этапы реализации.
